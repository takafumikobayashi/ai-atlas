# データ更新手順

掲載データを追加・更新するときの手順です。データの構造とルールは [data-schema.md](data-schema.md) を参照してください。

## 1. 調査する

1. 対象サービスについて、[service-candidates.md](service-candidates.md) の「採否を決める前に確認すること」を確かめる。
2. 公式の一次情報を開き、事実ごとに次を記録する。
   - ページの正確なURL
   - 確認日（実際にページを見た日）
   - ページの表示言語
   - そのページで確認できた事実
3. 地域・プラン・環境・言語によって変わる情報は、確認した条件をそのまま残す。
4. 公式情報で確認できなかった項目は `unknown` のままにする。推測で埋めない。

## 2. 記録する

1. `data/services.json` の `services` にレコードを追加する。
2. まず `evidence` に情報源を登録し、各主張の `evidenceIds` から参照する。
3. 状態値の使い分け：
   - `supported`：利用できることを公式情報で確認できた
   - `conditional`：条件付きで利用できる。条件を `conditions.ja` に具体的に書く
   - `unsupported`：利用できないことを公式情報で確認できた。ページに記載がないだけでは使わない
   - `unknown`：上記以外
4. 機能を同じチャット内で使えない場合は、`delivery` を `separate_product`／`integration`／`api_only` にする。
5. 「得意」などの主張は `capabilities` ではなく `strengthClaims` に書き、提供元の主張か編集部の所見かを区別する。
6. 掲載する理由を `inclusionReason.ja` に書く（任意。ただし推奨）。

## 3. 検証する

```sh
npm run validate          # 構造・語彙・根拠のチェック
npm run validate -- --strict   # 「要再確認」の警告もエラーにする（公開前に使う）
```

エラーをすべて解消してください。警告（確認日が古い、どこからも参照されない根拠など）も、公開前には対応するか理由を確認します。

画面での見え方は次の手順で確認します。

```sh
npm run dev               # http://localhost:4173/
```

## 4. レビューする

公開データの変更は、別の人（または別のセッション）が根拠URLを開き、記録した内容と一致しているかを確かめてから反映します。特に料金・提供地域・`unsupported` の主張を重点的に確認します。

## 5. 更新・終了・名称変更

- 情報が変わったら、値と `checkedAt` と根拠を更新する。古い根拠が不要になったら `evidence` から外す。
- 名称が変わったら、`id` は変えずに `name` を更新し、旧名を `aliases` に追加する。
- 提供が終了したら、レコードは消さずに `lifecycle.status` を `discontinued` にして根拠を付ける。一覧には表示されなくなる。
- 少なくとも四半期に一度、全レコードを見直す（`npm run validate -- --strict` で古い主張を洗い出せる）。料金と提供条件は公開直前にも再確認する。

## 6. 公開する

```sh
npm run build             # 検証のあと dist/ を作成（架空データは含まない）
npm run preview           # dist/ をローカルで確認
```

`dist/` の中身を静的ホスティングに配置します。
